# Claimed Submit Confirmation Packet Verifier

## Business Objectives And Boundaries
Provide a read-only preflight verifier for operator confirmation packets before a protected `resolve_stuck_submission` action can be considered. The verifier must never mutate order state, exchange state, Redis, Postgres, strategy configuration, risk gates, provider settings, symbols, venues, or strategy families.

## Module Responsibilities And Domain Model
`scripts/verify_operator_confirmation_packet.py` validates a no-secret confirmation packet against a runtime truth artifact. The domain object is the claimed-submit stuck order: local order is `SUBMITTING`, submit command is `CLAIMED`, no venue/exchange order id exists, no fills exist, latest reconciliation still halts, and operator confirmation is required.

## Input/Output Interfaces
Inputs are `--packet`, `--runtime-truth`, and optional `--operator-confirmation`. Output is JSON containing `valid`, `ready_for_protected_recovery`, `status`, failures, warnings, exact confirmation text, evidence hash, and order identifiers.

## Database Schema / Tables / Indexes / Constraints
No schema, table, index, or constraint changes. The verifier consumes runtime truth artifacts generated by existing runtime probes.

## Transactions, Consistency, Concurrency
No transactions. Consistency is checked by comparing packet evidence to current runtime truth and by validating the packet evidence SHA-256.

## Authorization, Authentication, Data Security
The verifier does not authenticate to the live API or database. It does not read env files or secrets. Confirmation strings are operational guard text, not credentials.

## Error Handling And Idempotency
Invalid or stale evidence returns JSON failures and exit code `2`; valid evidence returns exit code `0`. Re-running the verifier is idempotent.

## State Transition And Lifecycle
No state transitions are performed. A matching packet without operator confirmation remains `awaiting_external_operator_confirmation`; a matching packet with exact confirmation becomes `ready_for_protected_recovery`.

## Caching And Performance
The verifier reads two local JSON files and performs constant-size comparisons. No caching is needed.

## Logging, Monitoring, Auditing
The JSON result is the audit output. It is designed to be preserved alongside runtime truth and confirmation packet artifacts.

## Testing Strategy
Unit tests cover valid packet awaiting confirmation, exact confirmation readiness, runtime fill mismatch, evidence hash tampering, and wrong operator confirmation.

## Migration, Rollback, Compatibility
No migration. Rollback is deleting or reverting the script and tests. Existing runtime and operator APIs are unchanged.

## Configuration And Environment Isolation
No runtime configuration is required. The script runs with the repository Python environment and local artifact paths.

## Code Organization And Dependencies
The script uses only Python standard library modules and lives under `scripts/`; tests live under `tests/unit/scripts/`.

## Documentation And Operations Manual
Operators should run the verifier against the latest runtime truth and confirmation packet before using the protected recovery endpoint. If the verifier reports any failure, do not execute recovery.

## Deployment And Acceptance Criteria
Deployment is optional because this is a read-only local script. Acceptance requires focused unit tests to pass, JSON output to be valid, and no live order mutation.
