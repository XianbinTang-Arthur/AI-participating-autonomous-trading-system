## T+1 (UTC ~12:50) · 发现 & 修复 PG 60s safety net 副作用

### 事故
扫 `scripts/diag/pg_connection_health.sh` 时意外发现：
```
total_advisory_locks = 0  -- 应该是 4！
```

即 afddc1a 的 `idle_in_transaction_session_timeout=60s` 把 4 个 per-process
`single_runtime_lock` 连接**误杀**了。4 个进程 healthy 但单实例保护失效 ——
若启动第二个 gateway 会双跑。

### 根因
`aats/storage/session.py:127-141` acquire_single_runtime_lock：
```python
connection = self.engine.connect()
connection.execute(text("SELECT pg_try_advisory_lock(:k)"), ...).scalar()
# SA 2.0 autobegin tx → connection 处于 idle_in_transaction
```
PG 60s timeout 看到 idle-in-tx → terminate → pg_try_advisory_lock 是
**session-level**（connection close 时释放锁）→ lock 丢失。

### 修复（`23c8e7e`）
acquire 成功后立即 `connection.commit()`：
- connection 状态 idle_in_transaction → idle
- 60s timeout 不对 idle 生效
- advisory_lock 是 session-level（vs xact-level），commit 不释放锁

### 验证
```
advisory_lock_count=4      ← 修复前 = 0
idle_tx_with_advisory=0    ← 修复前 = 4 会积累到 0（被杀）
```
4 locks 正常持有，0 idle-in-tx（不再被 PG 60s 误杀）。

### 教训写进 `docs/weekly_review/` 模板
这是我**没做**的 audit：afddc1a deploy 后我只验证了"gateway 连接 timeout=1min"，
没验证**副作用**——自己的代码里哪些连接本来就是长期 idle-in-tx 设计，
会被误杀。下次：**加全局 safety net 时必须扫一遍仓库所有"长期持连接"的 pattern**。

## T+3 (UTC ~13:30) · Tier 2 审计 + 发现 & 修复 `_cached_ttl` / `_cached` TOCTOU 惊群

### 发现的 bug（存量 latent issue）

`aats/services/operator/query_service.py` 里的 `_cached`（L151-181）和
`_cached_ttl`（L217-282）singleflight 实现有一个 TOCTOU race，在高并发
下会让 singleflight "名存实亡"：

```python
# 旧写法（有 bug）：
try:
    value = loader()
finally:
    with self._cache_lock:
        self._inflight.pop(key, None)
        event.set()          # ← 先唤醒 follower
    # 🔴 race window 从这里开始：锁释放了、cache 还没写
with self._cache_lock:       # ← 再获锁写 cache
    self._ttl_cache[key] = ...
```

时间线：
1. Leader 跑完 loader，进 finally，获锁，`event.set()` 唤醒所有 follower
2. Leader 释放锁（退出第一个 `with` 块）
3. Leader 再去获取第二个 `with` 锁来写 cache
4. 同一刻 follower 也在抢同一个锁来读 cache
5. **如果 follower 抢赢**：读 `_ttl_cache` → 为空 → 回落到 `return loader()`
6. Leader 最后才写 cache，但已经晚了

理论效应：singleflight 本应挡住 N-1 次 loader，实际变成 N 次（惊群放大
1→N+1）。在生产观察到的 parallel_fetch_slow 现象里，这个 race 是
"隐形放大器" —— 根因已解（full-scan），但这个 race 仍让 UI 冷启动 P99
比理论值高。

### 修复（`query_service.py` 内联修复）

把 cache 写入和 `event.set()` 合并到同一个 critical section：

```python
try:
    value = loader()
except BaseException:
    # Leader 失败：唤醒 follower，不写 cache，让 follower 走兜底路径
    with self._cache_lock:
        self._inflight.pop(key, None)
        event.set()
    raise
# Leader 成功：cache 写入 + event.set() 在同一个 lock 里原子发生
with self._cache_lock:
    self._ttl_cache[key] = (...)
    self._inflight.pop(key, None)
    event.set()
return value
```

关键保证：follower 被 `event.set()` 唤醒后，再去拿 `_cache_lock` 时，
**cache 一定已经写入了**（因为 leader 释放锁才能让 follower 获锁，而 leader
释放锁的时候 cache 已在锁里写过了）。

### 确定性测试（`tests/unit/test_cached_ttl_toctou.py`）

用 `_SlowEvent` 子类人为把 `event.set()` 后面加 50ms sleep（只在测试里
替换），把 race 窗口拉到 50ms（生产里只有微秒级）。然后启动 1 leader +
5 follower 抢同 key，断言 loader 仅被调用一次。

3 个测试：
- `test_cached_no_thundering_herd_under_event_set_race` - `_cached` 路径
- `test_cached_ttl_no_thundering_herd_under_event_set_race` - `_cached_ttl` 路径
- `test_cached_ttl_leader_exception_wakes_followers` - leader 抛异常时必须
  唤醒 follower 避免 25s 死等

**结果**：全部通过 ✅。完整单测 2770 passed, 29 skipped, 0 failed, 耗时 6m21s。

### 做了什么、没做什么

做了：
- ✅ 审计 `_cached_ttl` 所有 40+ 个调用点（主要在 operator/query_service、
  operator/account_queries、operator/strategy_queries、operator/report_queries、
  operator/recovery_queries、operator/lifecycle_attribution）
- ✅ 确认 bug 理论上存在 + 写出复现测试 + 修复 + 验证
- ✅ 加锚点测试防止未来 regression

没做（避免过度）：
- ❌ 动 follower 端的 `return loader()` 兜底路径 —— 那条路径是 leader 真正
  失败时的正确 fallback，不能改
- ❌ 把 `_cache_lock` 换成带 fairness 的锁 —— 当前 Python `threading.RLock`
  在大多数场景下足够，不值得为这个引入 queue lock
- ❌ 改动 `_SINGLEFLIGHT_WAIT_SECONDS = 25s` 常量 —— 有 anchor test
  （`test_singleflight_wait_constant.py`）守着

### 教训

这是一个**存量 latent issue**，不是我今天引入的。但仍然记录进
`docs/weekly_review/_template.md` 作为"AI 必须主动审计 latent
concurrency bug"的示例：

> 写代码时的"finally 里先释放信号再写入结果"看似顺理成章，但只要持有
> 结果的状态写入**不在同一个 critical section**，就会造成 TOCTOU race。
> AI 的过去代码审查、包括我自己之前多轮改 query_service.py 都没抓到，
> 只有今天有时间主动做"singleflight 扫一遍"时才找出来。

### 修复方向（⚠ 等用户审批 — 涉及 safety-critical 信号语义）

保守可选方案（按风险由低到高）：

1. **dedup at publish time** — `guard_signal_cache.py` 计算 payload hash，
   如与上次相同则跳过 event_store 持久化（仍然更新 Redis/NATS heartbeat）。
   风险：下游如果依赖 "每 13s 一次" 做 staleness 检测，dedup 会误触发。
2. **独立 event_type 拆分** — `RecoveryStatusSummary`（booleans，小）每 13s
   publish；`RecoverySnapshotDetail`（snapshots 数组，大）仅在 snapshot hash
   变化时 publish。风险：需要两个 event_type 的消费者协调更新。
3. **不持久化，只走 NATS** — 既然是 "current state" 不是 "history"，可以只
   走 NATS ephemeral 广播；历史审计从 reconciliation_snapshots 等重建。风险：
   丢失完整审计追溯。

### 我的判断

铁律"**绝不改 kill switch / recovery policy 语义字段**"。`recovery` 信号
controls RiskEngine 的 only-reduce 决策，任何对它的 publish 行为改动都是
语义敏感。**不动。**
