# Task22：AATS 前端展示重构方案与 Codex 实施提示词

## 1. 任务背景

当前项目的前端控制台已经具备了较完整的运营能力：

- 健康状态与运行姿态查看
- 决策、订单、成交、对账、恢复、操作员管理等多视图访问
- 中文化和基本的视觉体系

但从专业交易终端与专业产品设计的角度看，当前 UI 仍然存在明显问题：

- 信息过多，但优先级不清晰
- 交易语义对普通人不够友好，理解成本高
- “策略、执行、风险、恢复、权限”混在同一平面上
- 数据很多，但缺少“现在系统在做什么、为什么、风险在哪里”的清晰叙事
- `app.js` 过于庞大，状态、数据抓取、格式化、渲染、交互绑定高度耦合
- 页面结构更像“工程控制台”，还不像“交易控制台”
- 对关键交易对象缺少更强的视觉层级，比如：
  - 当前可否交易
  - 当前仓位与权益
  - 最新一笔决策为何开/不开
  - 最新订单处于什么阶段
  - 当前是否需要人工介入

这个任务的目标，不是做一个花哨的后台，而是把当前 UI 重构成一个**专业、可信、交易语义清晰、具备运维可操作性**的交易控制终端。

---

## 2. 当前 UI 的主要问题

### 2.1 信息架构问题

当前的主要问题不是“功能缺失”，而是“信息组织方式不对”。

具体表现：

- 顶部信息条、命令条、主工作区同时都在承载“核心信息”，导致视线没有主次
- Overview 页承载了太多不同性质的信息：
  - 系统状态
  - 账户状态
  - 决策摘要
  - 阻断原因
  - 恢复状态
  - 指标和时间线
- Diagnostics 页和 Overview 页语义边界不够清晰
- Operators 和 Runtime Profiles 属于管理面，但在主工作区中的定位不够“后置”

### 2.2 交易语义问题

当前 UI 中有不少术语仍偏工程内部语义，而不是交易员或运营者语义。

例如：

- “运行姿态”对普通用户不够直观
- “提交通道”与“执行通道”容易混淆
- “对账 clean / mismatch / review_required”没有被翻译成“对交易意味着什么”
- “rebaseline / resume / halt”缺少明确后果说明

用户真正关心的问题通常是：

- 现在能不能交易？
- 为什么不能交易？
- 当前仓位是什么？
- 当前是赚钱还是亏钱？
- 最新一次策略在做什么判断？
- 最新一笔订单执行到哪一步了？
- 我是否需要人工干预？

### 2.3 布局问题

当前页面更像“卡片拼接”，而不是“专业交易控制界面”。

问题包括：

- 顶部内容高度过大，首屏有效信息密度不够
- 操作按钮虽然齐全，但重要性层级不够
- 缺少“主监控区”和“次监控区”的明确分工
- 缺少“持续关注信息”和“按需查看信息”的区分
- 表格和卡片视觉风格接近，导致不同信息类型不容易快速分辨

### 2.4 前端实现问题

当前前端实现对继续演进不友好。

主要问题：

- `aats/api/static/app.js` 是典型的大型单文件
- 数据请求、状态存储、字段格式化、组件渲染、行为绑定混在一起
- view 间的逻辑复用和共享格式化缺少明确边界
- UI 文案、术语映射、状态颜色、组件生成逻辑耦合严重
- 后续如果继续增加图表、筛选、告警、移动端适配，维护成本会继续升高

### 2.5 编码与中文稳定性问题

当前项目已经在路由层显式输出 `charset=utf-8`，这是对的，但仍应把“中文稳定显示”作为设计基线，而不是附带结果。

需要长期稳定做到：

- HTML / JS / CSS 文件统一为 UTF-8
- Windows 环境下避免中文乱码
- UI 术语统一收敛到一处
- 前端不要散落大量难维护的中文状态词

## 3. 重构目标

新 UI 应达到以下目标：

### 3.1 业务目标

- 让非开发背景的操盘者也能快速理解系统状态
- 把“交易资格、风险阻断、账户权益、策略动作、执行进展”放到最前面
- 让人工介入操作更慎重、更明确、更可追溯

### 3.2 产品目标

- 从“工程控制台”升级成“交易控制终端”
- 文案统一、语义清晰、状态可解释
- 视觉上更专业、更可信、更像金融级后台

### 3.3 工程目标

- 拆分 `app.js`，降低耦合
- 形成组件化渲染结构
- 形成统一的设计 token、状态颜色、文案映射和格式化工具
- 为后续继续加入图表、筛选、告警和移动端适配留出空间

## 4. 重构后的信息架构

建议把当前页面重构为 5 个一级工作区，而不是现在这种“平铺型工作区”：

### 4.1 总览

目标：首屏 10 秒内回答“系统现在能不能安全交易”。

首屏必须突出：

- 当前交易资格
- 当前运行状态
- 当前权益 / 持仓 / 当日收益
- 最新策略动作
- 最新订单执行状态
- 当前风险阻断或人工复核要求

建议结构：

1. 顶部总控头部
   - 品牌区缩小
   - 当前会话信息简化
   - 运行状态、交易资格、提交模式做成高辨识度状态条

2. 第一屏核心卡组
   - 交易资格卡
   - 账户权益卡
   - 当前持仓卡
   - 最新策略卡
   - 最新执行卡
   - 风险阻断卡

3. 第二屏监控区域
   - 最近 24h 收益概览
   - 最新异常 / 告警
   - 最新对账结果
   - 恢复与基线状态

### 4.2 策略决策

目标：把“为什么做出这个判断”解释清楚。

建议展示：

- 当前市场状态（趋势 / 突破 / 震荡 / 不确定）
- 决策方向（做多 / 做空 / 保持 / 不交易）
- 目标仓位与当前仓位差异
- 信号组成：
  - alpha 评分
  - baseline confidence
  - microstructure 是否支持
  - AI 是否参与
- 交易门禁：
  - 成本门是否通过
  - regime 是否允许
  - risk 是否通过
- 最近决策时间线

这个页面应更像“策略解释器”，而不是“事件明细堆栈”。

### 4.3 订单与执行

目标：把一笔交易从意图到成交的生命周期看清楚。

建议展示：

- 当前活动订单
- 最近成交
- 执行错误
- 订单状态流
  - CREATED
  - SUBMITTING
  - SUBMITTED
  - PARTIALLY_FILLED
  - FILLED
  - CANCEL_PENDING
  - CANCELED / FAILED / REJECTED
- 同一订单的时间线与错误原因
- “卡住的订单”与人工处理入口

这个页面要从“数据列表”升级成“订单生命周期面板”。

### 4.4 账户、风险与对账

目标：把资金安全与系统可信度讲清楚。

建议拆成三个面板：

- 账户面板
  - 总权益
  - 可用 / 占用 / 冻结
  - 现货 / 合约持仓
  - 未实现 / 已实现收益

- 风险面板
  - 当前风险状态
  - 当前限制
  - 触发中的 blocker
  - 是否可恢复交易

- 对账与恢复面板
  - 最新对账状态
  - mismatch 分类
  - 是否需要人工复核
  - baseline / rebaseline / recovery 状态

### 4.5 管理与权限

目标：把管理能力放在“次级区域”，降低误触风险。

包含：

- 操作员账户管理
- 权限状态
- 当前会话与最近登录
- runtime profiles
- 高风险动作统一收口

高风险操作：

- halt
- resume
- rebaseline
- 手动 validate
- stuck submission resolve

必须统一使用：

- 显式确认弹窗
- 后果说明
- 当前条件说明
- 操作结果回执

## 5. 视觉设计方向

### 5.1 整体基调

建议保留深色主题，但重做视觉方向，使其更接近专业交易终端，而不是科技风大屏。

建议方向：

- 深海军蓝 + 冷灰 + 琥珀 / 绿色 / 红色状态色
- 减少紫色存在感
- 减少“炫光感”，强化“可信、稳定、金融级”

### 5.2 字体体系

建议：

- 标题：`Aptos Display` / `Segoe UI Variable Display` / `PingFang SC`
- 正文：`Aptos` / `Segoe UI Variable` / `PingFang SC`
- 数字与交易字段：`JetBrains Mono` / `Cascadia Mono`

重点：

- 资金、仓位、PnL、价格、订单数量必须明显使用等宽数字或至少视觉稳定的数字风格
- 中文标题应避免过度花哨

### 5.3 状态颜色系统

建议统一状态色：

- 正常 / 可交易：绿色
- 注意 / 退化：琥珀色
- 阻断 / halted / mismatch：红色
- 信息 / 同步中 / 审计中：蓝色
- 中性 / 待定：灰蓝

并统一映射：

- 颜色
- 背景
- 边框
- 图标
- 文案

### 5.4 页面节奏

建议从现在的“块状拼贴”重构为“主叙事 + 次诊断”的节奏：

- 首屏：最关键决策信息
- 中段：策略、执行、风险摘要
- 下段：历史、时间线、明细

不要让用户一进页面就先被几十个同权重卡片淹没。

## 6. 文案重构原则

UI 文案必须从“工程状态名”翻译成“交易可操作语言”。

例如：

- `halted`
  - 不是“halted”
  - 而是“系统已暂停交易”

- `resume_blocked`
  - 不是“恢复受阻”
  - 而是“当前还不能恢复交易”

- `review_required`
  - 不是“需要复核”
  - 而是“需要人工确认后才能继续”

- `execution_blocked`
  - 不是“执行阻断”
  - 而是“当前不允许发单”

- `reconciliation mismatch`
  - 不是“mismatch”
  - 而是“本地记录与交易所状态不一致”

收益相关文案必须明确区分：

- 总权益
- 已实现收益
- 未实现收益
- 当日收益
- 手续费
- 持仓方向
- 当前仓位价值

## 7. 前端技术重构建议

### 7.1 技术策略

当前不建议直接引入大型前端框架，除非项目准备正式拆出前端工程。

更稳妥的路线是：

- 继续使用静态资源 + 原生 ES Modules
- 在现有 `aats/api/static` 基础上拆模块
- 保持服务端路由简单
- 降低部署复杂度

### 7.2 推荐的前端目录结构

建议把当前的 `app.js` 拆分成如下结构：

```text
aats/api/static/
  app.js
  app.css
  login.js
  modules/
    api-client.js
    store.js
    terms.js
    formatters.js
    badges.js
    dialogs.js
    view-router.js
    views/
      overview-view.js
      strategy-view.js
      execution-view.js
      risk-view.js
      operators-view.js
    components/
      stat-card.js
      status-bar.js
      timeline.js
      data-table.js
      detail-drawer.js
      alert-banner.js
      action-panel.js
```

### 7.3 代码职责划分

- `api-client.js`
  - 统一请求和错误处理
- `store.js`
  - 管理页面状态、缓存、刷新节奏
- `terms.js`
  - 统一中文术语映射
- `formatters.js`
  - 金额、时间、百分比、状态格式化
- `views/*.js`
  - 每个工作区一个独立渲染入口
- `components/*.js`
  - 复用 UI 组件

### 7.4 交互层要求

- 自动刷新不能打断用户正在看的详情抽屉
- 高风险操作必须二次确认
- 错误消息必须区分：
  - 拉取失败
  - 权限不足
  - 系统阻断
  - 数据不存在
- 详情抽屉应支持：
  - 决策详情
  - 订单详情
  - 成交详情
  - 对账详情
  - 恢复详情

### 7.5 中文稳定显示要求

必须明确要求：

- 所有静态文件统一保存为 UTF-8
- 路由响应头继续显式输出 `charset=utf-8`
- 所有中文状态文案集中管理，不在各视图散落硬编码
- 避免再出现“页面能显示、终端里一团乱码、维护时极难改文案”的情况

## 9. 交付标准

重构完成后，至少应满足：

1. 首屏 10 秒内可以回答“当前能否交易”
2. 首屏 15 秒内可以回答“为什么不能交易”
3. 用户可以在 20 秒内看懂：
   - 当前仓位
   - 当前权益
   - 最新策略动作
   - 最新订单状态
4. 文案不再依赖工程内部术语理解
5. `app.js` 不再是单体巨文件
6. 中文显示稳定，不出现乱码与术语漂移
7. 高风险动作有明确确认与后果提示

## 背景理解

这是一个事件驱动的加密交易系统原型，前端主要面向：

- 策略观察
- 订单执行监控
- 账户和收益查看
- 风控阻断查看
- 对账、恢复、人工干预
- operator 用户和 runtime profile 管理

前端页面已有很多数据接口，但当前主要问题是：

- 信息架构混乱
- 工程术语过多
- 视觉层级不足
- `app.js` 过大且耦合严重
- 页面更像工程控制台，不像交易控制终端

## 设计目标

你必须把页面重构成以下结构与体验：

### 1. 总览页

首屏必须优先回答：

### 1. 不要保留单体 `app.js`

请把前端拆成多个模块，但保持现有静态前端交付方式，不要默认引入大型框架。

推荐结构：

```text
aats/api/static/
```
