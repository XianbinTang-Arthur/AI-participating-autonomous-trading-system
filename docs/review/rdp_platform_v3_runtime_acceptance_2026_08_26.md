## 2. 重构范围

### 2.1 后端

- 新增 `rdp.workspace.v3` 聚合契约和 `GET /rdp/v3/workspace`，一次读取形成运行、研究、发布、观察四个操作面板。
- 明确任务生命周期：请求已接收、排队、执行、成功、失败、取消；活跃任务不会因分页而从 UI 消失。
- 区分工作流成功与研究结论：`succeeded + blocked_by_attribution` 表示流程执行完整，但证据不足以发布。
- 推荐项携带稳定的 `source_round_id` 与目标参数集，避免后续决策轮次覆盖推荐来源。
- 候选、发布和观察从治理数据库读取；文件只保留兼容和证据用途。
- 发布资格收紧为：仅 `parameter_upgrade`、状态已批准、Gate 通过、数据库读取新鲜。
- Step2 完整性在前端摘要和后端写接口共用同一评估器；无快照、清单缺失、查询失败均 fail-closed。
- 队列健康区分当前未恢复故障与历史失败审计记录，历史终态不再显示为当前积压。

### 2.2 前端

- RDP 页面拆分为格式化、生命周期、运行、研究、发布模块，移除单体渲染器中的重复判断。
- 操作面板以“现在能做什么、为什么不能做、下一步是什么”为主线，展示真实队列位置、执行槽位、步骤进度和研究结论。
- 审批、Gate、发布、观察、回滚按业务顺序解锁；前端禁用原因与后端拒绝原因保持一致。
- 高风险应用仍要求服务端签发并校验短时令牌；UI 测试只使用 mock 令牌，不产生真实凭证。

## 3. 成熟平台经验及采用边界

本次设计参考了 QuantConnect 的研究到回测分层、MLflow 的运行/指标/制品可追踪模型、Qlib Recorder 的实验记录、Optuna 的 trial 生命周期，以及 NautilusTrader 强调的研究与执行一致性。采用的是通用治理原则，而不是复制其产品结构：

| 成熟实践 | AATS 落地 | 未直接照搬的原因 |
|---|---|---|
| Run/Experiment 可追踪 | Run、Attempt、Step、Outcome 分层持久化 | AATS 还必须叠加资金安全和人工审批 |
| 研究与执行语义一致 | 统一参数谱系、发布 Gate、观察与回滚 | 交易所和账户状态属于运行时真相，不能只靠研究制品 |
| Trial 生命周期 | 推荐项状态机与稳定来源轮次 | 参数候选不能自动等价为可发布版本 |
| 制品与指标索引 | 决策轮次、归因、执行真实性统一入口 | 数据库为当前真相，文件不作为实时状态证明 |

## 6. 剩余风险与上线边界

1. 当前数据归因仍不足，RDP 只能提出草案，不能证明参数能产生稳定正收益。
2. `liquidation_no_data` 与 `partial_baseline` 表明微观结构样本不完整；需要先补齐数据并重新积累样本。
3. 生产账户、交易所连接、生产 schema、回滚闭环和交易就绪包尚未在本记录中验证。
4. 本地模拟栈健康不等于实盘可上线；任何实盘应用必须重新执行生产门禁并由人工审核。
5. 在出现合格候选前，正确动作是保持当前参数，不是为了完成流程而强行批准草案。
