# RDP UI 对齐与收口 SOW

## 背景

RDP 后端已经切到 DB-first 的控制链，`/rdp/control-summary` 也能稳定给出当前环境、待审批建议、待发布项、观察队列和阻断信息。当前 UI 的主要问题不在数据缺失，而在两个层面：

1. 主操作区没有按真实风险优先级排序，`rollback_recommended` 没有被提升成最高优先级动作。
2. 创建发布/运行观察仍然强制要求用户输入观察窗口时长，和后端已经给出的环境默认窗口重复，属于无意义交互噪音。

## 当前行为

- 命令条优先显示 `创建发布`，即使同一时刻已经存在 `rollback_recommended` 的 release。
- 参数候选卡片和治理建议卡片会在同一 combo 上重复出现，导致“一个待处理动作展示成两个工作项”。
- UI 主流程里创建发布和运行观察都会弹出 `window.prompt`，要求再次输入观察窗口小时数。

## 目标

1. 让命令条和待处理队列反映真实操作顺序：回滚建议 > 待发布 > 待审批 > 观察中。
2. 删除主流程中的冗余输入，发布/观察直接使用后端已经暴露的默认观察窗口。
3. 合并同一 combo 上“参数候选 + 治理建议”的重复工作项，保留一个能直接处理的核心卡片。

## 方案

### 1. 命令条优先级修正

- 当 observation queue 中存在 `rollback_recommended` 时，命令条主动作改为 `执行回滚`。
- 只有在没有回滚建议时，才显示 `创建发布` 或 `运行观察`。
- 命令条 headline 也优先反映回滚状态，而不是被一般性健康阻断覆盖。

### 2. 队列去重

- 对于同一 combo，如果同时存在参数候选 draft 和治理建议 draft：
  - 只保留一个候选卡片；
  - 卡片正文同时展示参数集和治理结论；
  - 卡片动作直接作用于治理建议，而不是再额外渲染一张治理卡片。

### 3. 观察窗口交互简化

- `创建发布` 默认使用 `environment.required_observation_window_hours`。
- `运行观察` 默认使用 release 自带的 `observation_window_hours`，没有时回退到环境默认值。
- UI 不再弹出 `prompt`，观察窗口覆盖需求保留给 CLI/API。

## 验证

- 更新 Node 渲染 smoke test，验证：
  - RDP 面板仍只保留核心区域；
  - 同 combo 不再额外渲染独立治理卡片；
  - rollback 状态会把命令条主动作切到回滚。
- 新增前端动作测试，验证：
  - 创建发布不再调用 `prompt`；
  - 运行观察不再调用 `prompt`；
  - 请求 body 使用正确的默认观察窗口。
