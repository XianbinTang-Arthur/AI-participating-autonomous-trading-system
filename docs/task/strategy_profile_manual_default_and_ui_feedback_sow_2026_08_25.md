## 1. 目标与验收标准

本任务解决两个相互关联的问题：操作员点击“手动切档”后，后端虽然已处理请求，页面仍出现自动管理的矛盾文案且缺少即时成功反馈；spot 与 derivatives 托管配置仍把自动换档设为默认值。完成后应满足：

1. 所有托管运行档案默认采用手动切档；只有显式修改配置并重启后才允许恢复自动切档。
2. 页面所有位置使用同一份有效运行态，不能同时显示“手动切档”和“自动管理”。
3. 成功切换后立即显示成功反馈，并把当前模式按钮标记为“（当前）”。
4. 配置总开关关闭时，前端禁用“自动切档”，后端也拒绝绕过配置开启自动控制。
5. 不改变当前活动策略档位，不触发下单、撤单或任何实盘资金操作。

## 2. 当前行为与根因

- `POST /strategy-profiles/pause-auto` 已幂等地把持久化激活状态改为手动；本地模拟栈的操作审计也记录了成功请求。
- “运行参数概览”把 `activeProfileMeta(..., true, ...)` 的自动标志写死为 `true`，因此即使控制面板已切到手动，该区域仍显示“当前正在自动管理这个档位”。
- 切换成功消息只写入页面状态，随后直接等待整页刷新；网络请求期间缺少即时可见反馈。
- Settings 模型默认值为手动，但 `spot.yaml` 与 `derivatives.yaml` 又显式覆盖为自动，造成默认语义不一致。
- 核心自动控制把配置值作为硬总开关，但运行态查询与恢复自动接口只看持久化覆盖，能形成“接口称已自动、核心实际仍禁用”的不一致状态。

## 3. 范围与边界

### 3.1 范围内

- 修正托管配置中的档位控制默认值和说明。
- 统一运行态查询、恢复自动接口与核心硬总开关的语义。
- 修正 AI 配置页的控制按钮、状态文案和成功反馈。
- 更新相关配置文档与静态页面说明。
- 增加或调整单元、API 集成和前端渲染回归测试。

### 3.2 范围外

- 不调整六个策略档位的交易参数、风控阈值或选择算法。
- 不迁移或重写既有策略档位历史、激活记录与操作审计。
- 不部署到实盘 profile，不解除当前 live 门禁，不执行交易副作用。
- 不处理工作区中其他前端审查改动。

## 4. 组件职责与数据流

- `configs/strategy_profiles/*.yaml`：声明部署启动时的配置默认值，是自动控制的静态硬门禁。
- `StrategyProfileActivationState.auto_switch_enabled`：记录配置允许自动控制时，操作员当前选择的运行态覆盖。
- `StrategyProfileControlService`：只有“配置允许且激活状态允许”时才执行自动评估/激活。
- `OperatorRuntimeQueries`：向 API/UI 输出配置态和有效态，不得把持久化残留误报成有效自动控制。
- `/strategy-profiles/pause-auto` 与 `/strategy-profiles/restore-auto`：提供管理员控制入口；前者幂等，后者必须服从配置硬门禁。
- AI 配置页：只展示服务端有效态，操作成功后刷新权威快照。

输入为管理员确认后的控制请求，输出为带 `status`、`activation`、`active_revision` 的 JSON，以及更新后的仪表盘快照。配置关闭时恢复自动返回 HTTP 409 和稳定错误码 `strategy_profile_auto_control_disabled_by_configuration`。

## 5. 数据、事务与并发

本任务不新增数据库表、列、Redis 键或迁移。激活状态继续使用现有仓储保存；切换接口保持现有串行执行、幂等返回和缓存失效流程。配置关闭时在任何状态写入之前失败，避免产生部分更新。现有并发与仓储原子性边界不扩大。

## 6. 权限、安全与审计

- 继续要求管理员权限、现有会话认证与 CSRF/来源校验。
- 成功切换继续写入操作员审计；配置门禁拒绝由现有 API 错误处理记录，不输出凭证或敏感配置。
- 不读取或展示 `.env.*` 内容，不在文档、日志或响应中写入账号身份和密钥。
- 本地验证仅使用 derivatives 模拟栈，不执行实盘资金操作。

## 7. 错误、幂等与状态生命周期

- 已是手动时再次暂停返回 `already_manual`，UI仍明确显示当前状态。
- 已是自动时再次恢复返回 `already_auto`。
- 配置为手动时恢复自动返回 409；不会修改 `auto_switch_enabled`、冻结时间或活动档位。
- 手动激活某档位仍暂停自动切换；恢复自动只改变控制模式，不立即换档。
- 页面刷新、重新登录和服务重启后均以 API 权威快照重新渲染。

## 8. 缓存、性能、日志与可观测性

不增加轮询频率、查询次数或高基数字段。成功写入继续失效现有策略档位缓存；页面沿用一次操作后的一次仪表盘刷新。验证关注 API 状态码、有效控制模式、按钮禁用状态和审计事件，不记录敏感载荷。

## 9. 测试方案

- 配置测试：四个托管 profile 均断言默认手动，生成配置与 Settings 加载结果一致。
- 运行态测试：配置关闭且持久化状态残留为自动时，有效态仍必须为手动并给出明确原因。
- API 测试：配置关闭时恢复自动返回 409 且不改变状态；配置开启时保留原有恢复行为；暂停操作保持幂等。
- 前端测试：手动按钮标注当前、自动按钮在配置关闭时禁用、档位按钮可用、概览不再显示自动管理、成功消息在刷新前立即渲染。
- 回归验证：Ruff、相关单元测试、最窄 API/前端集成测试以及完整单元测试；WSL2 集成环境可用时再执行对应测试。

## 10. 兼容性、迁移与回滚

这是有意收紧的安全兼容变化：过去可在配置关闭时通过 API 把持久化状态写成自动，修复后返回 409。调用方若确需自动控制，必须先把托管 profile 中 `strategy_profile_auto_control_enabled` 改为 `true`，经标准提交、同步和重启流程生效，再调用恢复接口。

无需数据迁移。旧数据库中即使残留 `auto_switch_enabled=true`，运行态也会在配置关闭时解释为手动；不会破坏历史审计。代码回滚可恢复旧行为，配置回滚则需显式恢复旧值并重新部署。当前改动在提交部署前不会改变已运行容器。

## 11. 配置、依赖、文档与运维

不新增环境变量或第三方依赖。同步更新托管配置说明和管理配置参考，明确“配置硬门禁”和“操作员运行态覆盖”的优先级。部署仍只允许使用项目标准脚本；本任务不直接部署、不手工运行 Docker Compose。上线验收必须分别验证配置值、`/system/health`、策略档位 API 有效态与页面显示，不能仅以 `/healthz` 作为完成证据。
