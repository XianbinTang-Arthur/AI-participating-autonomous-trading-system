# Task59 下一阶段项目任务书

> 项目定位声明：本文件默认服从 AATS 的统一目标：在严格风控、可审计、可恢复、可治理前提下，通过自动化交易追求长期稳定盈利，为 AI 的持续自治与终身发展积累资本。详见 [项目定位声明](../../../docs/project_positioning.md)。


## 1. 任务名称

交易收益验证与小资金实盘准备项目

## 2. 项目背景

截至 Task58，系统已经完成五阶段重构，并进入 `financial_convergence_mode_enabled` 收敛线。当前系统相较早期版本，已经显著提升了以下能力：

- 执行主真相已迁移到 `execution_orders / execution_fills`
- 余额主真相已迁移到账本侧 `ledger_journals / ledger_entries`
- 恢复、对账、控制面已经具备 `execution + ledger` 视角
- 保留金、结算、lots、operator 控制与审计能力均已建立基础

但这套改造主要解决的是“系统是否可信、可恢复、可审计、可控”，并没有直接证明“策略是否具备稳定正收益”。因此，下一阶段项目重点不再是继续扩展底层架构，而是把项目推进到“可以严肃验证是否赚钱”的阶段。

## 3. 项目目标

本阶段目标不是立即追求资金规模放大，而是完成从“安全底座已成型”到“具备收益验证闭环”的切换。

具体目标如下：

1. 建立真实交易收益验证闭环
2. 建立执行质量与交易成本归因体系
3. 建立策略分层评估与退化检测机制
4. 建立小资金、强风控、可回滚的实盘试运行方案
5. 给出是否进入下一阶段资金放大的客观准入标准

## 4. 本阶段核心问题

当前距离“项目可以赚钱”还差的，不是底层真相源，而是以下四类验证：

1. 策略是否真的有 alpha
2. 实盘滑点、手续费、延迟是否吃掉 alpha
3. 风控参数是否足以在坏行情中保住本金
4. 长时间运行下，收益是否稳定而不是偶然

本阶段必须把这四类问题变成可量化、可回放、可审计的数据结果。

## 5. 项目范围

### In Scope

- 收益验证指标体系
- 执行质量指标体系
- 策略分层评估报表
- 小资金试盘控制方案
- 自动停机与策略退化检测
- 周期性复盘与放量准入机制

### Out of Scope

- 新增大规模策略品类
- 引入新的交易所
- UI 大改版
- 无验证前提下直接扩大资金规模
- 在没有前向验证结果前做收益宣传或规模化部署

## 6. 主要交付物

### 交付物 A：交易收益验证报表

必须能按日、周、月输出：

- 总收益
- 净收益
- 手续费总额
- 滑点总额
- 成交成功率
- 平均持仓时间
- 单笔平均盈亏
- 胜率
- 盈亏比
- 最大回撤
- 风险调整后收益

### 交付物 B：执行质量归因报表

必须能针对每笔订单输出：

- 信号生成时间
- 计划价格
- 下单时间
- 交易所确认时间
- 实际成交价格
- 成交延迟
- 信号价到成交价偏差
- 计划价到成交价偏差
- 费用占名义成交额比例

### 交付物 C：策略分层表现评估

必须按以下维度切分：

- 市场状态：趋势 / 震荡 / 高波动 / 低流动性
- 品种
- 时间段
- 多空方向
- 开仓类型：首次开仓 / 加仓 / 减仓 / 平仓 / 反手

输出每个切片下的：

- 交易次数
- 净收益
- 手续费拖累
- 滑点拖累
- 最大连续亏损
- 是否达到继续启用阈值

### 交付物 D：小资金试盘运行方案

必须明确：

- 初始资金上限
- 单笔最大仓位
- 单日最大亏损
- 单周最大亏损
- 连续亏损停机阈值
- 对账失败停机阈值
- 策略退化停机阈值
- 人工复核流程

### 交付物 E：放量准入标准

必须形成书面准入条件，至少包括：

- 前向验证样本量
- 最长允许回撤
- 最低净收益阈值
- 最低成交质量阈值
- 最低对账稳定性阈值
- 最低恢复成功率阈值

## 7. 工作分解结构

### 模块 1：收益与成本数据面建设

目标：把“赚了还是亏了”拆成可解释的数据项。

任务：

- 统一记录 signal price、reference price、submit price、fill price
- 统一记录 fee、slippage、latency
- 补充订单到成交的因果链路字段
- 给 operator 查询层增加收益/成本聚合接口

输出：

- 新增收益归因数据模型
- 新增执行质量聚合查询
- 新增日级/周级收益报表接口

### 模块 2：策略验证框架

目标：把策略评价从“看总收益”升级为“看分层稳定性”。

任务：

- 增加市场状态标签回填
- 增加策略动作分类统计
- 增加滚动窗口表现分析
- 增加收益退化检测与告警

输出：

- 策略表现分层报表
- 滚动窗口退化检测器
- 策略暂停建议规则

### 模块 3：执行质量治理

目标：确认执行层没有吞掉策略 edge。

任务：

- 统计 submit 到 ack 延迟
- 统计 ack 到 fill 延迟
- 统计计划价与成交价偏差
- 统计取消率、重试率、失败率
- 识别高成本订单模式

输出：

- execution quality dashboard 数据接口
- 高滑点 / 高延迟 / 高费用订单诊断视图

### 模块 4：小资金试盘与风控收口

目标：让系统具备有限真实资金前向验证能力。

任务：

- 定义试盘资金上限
- 定义强风控参数模板
- 增加日损/周损自动停机
- 增加连续亏损自动停机
- 增加策略退化自动停机
- 增加人工恢复门禁

输出：

- trial runtime profile
- 试盘运行手册
- 自动停机条件与 operator 操作说明

### 模块 5：准入评审机制

目标：明确什么时候可以从试盘进入更大资金阶段。

任务：

- 建立阶段性评审模板
- 固化放量准入条件
- 固化回退条件
- 固化事故复盘模板

输出：

- 资金放量评审模板
- 继续运行 / 缩容 / 停机三类决策模板

## 8. 实施顺序

建议按以下顺序执行：

1. 先做收益与成本数据面
2. 再做策略验证框架
3. 再做执行质量治理
4. 再做小资金试盘与自动停机
5. 最后做放量准入评审机制

原因：

- 没有统一数据面，就无法判断策略是否赚钱
- 没有分层评估，就无法判断收益是否稳定
- 没有执行质量归因，就无法判断亏损来自策略还是执行
- 没有停机和回退条件，就不应该上真实资金

## 9. 验收标准

本阶段完成的最低验收条件如下：

1. 任意一笔实盘交易都能回答：
   - 为什么下单
   - 计划价格是多少
   - 实际成交价格是多少
   - 手续费和滑点是多少
   - 这笔交易最终赚亏多少

2. 系统能输出至少 30 天前向验证报表，包含：
   - 日收益
   - 周收益
   - 最大回撤
   - 胜率
   - 盈亏比
   - 手续费占比
   - 滑点占比

3. 系统能自动识别并停机以下情况：
   - 日损超阈值
   - 周损超阈值
   - 连续亏损超阈值
   - 策略退化超阈值
   - 对账失败持续发生

4. 能形成书面结论：
   - 当前策略是否具备小资金持续试盘资格
   - 当前策略是否具备放量资格

## 10. 风险与约束

### 风险

- 策略本身可能没有持续正期望
- 执行成本可能显著高于回测假设
- 小样本盈利可能是偶然
- 市场切换后策略表现可能迅速退化

### 约束

- 不允许跳过前向验证直接放大资金
- 不允许在报表缺失的情况下做收益判断
- 不允许在停机条件不完善的情况下进入无人值守真钱运行

## 11. 建议里程碑

### M1：数据面完成

- 收益归因字段齐全
- 执行质量字段齐全
- 查询接口可用

### M2：验证报表完成

- 日/周收益报表可用
- 成本归因报表可用
- 市场状态分层报表可用

### M3：试盘控制完成

- 自动停机规则上线
- 人工恢复流程确定
- trial runtime profile 可用

### M4：前向验证完成

- 至少积累一段连续真实运行样本
- 形成是否继续投入资金的结论

建议马上进入以下具体任务：

1. 新增收益归因模型与聚合查询
2. 为每笔订单补齐 signal/plan/submit/ack/fill 时间与价格链路
3. 新增执行质量报表接口
4. 新增策略分层收益报表接口
5. 新增试盘专用 runtime profile 与自动停机规则
6. 新增前向验证周报模板

## 13. 结论

当前项目已经基本完成“系统可信性”这一层的主要重构，下一阶段不应继续把主要精力放在底层架构扩张上，而应集中到“收益验证、执行质量、试盘控制、放量准入”四件事。

从项目管理角度看，Task59 的目标不是继续让系统“更复杂”，而是让团队可以用客观数据回答一个真正关键的问题：

这套系统到底有没有能力，在真实交易约束下，持续产生可接受的净收益。
