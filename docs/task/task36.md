# Task36 前端全量诊断与收口方案

> 项目定位声明：本文件默认服从 AATS 的统一目标：在严格风控、可审计、可恢复、可治理前提下，通过自动化交易追求长期稳定盈利，为 AI 的持续自治与终身发展积累资本。详见 [项目定位声明](../../docs/project_positioning.md)。


## 1. 背景

当前前端已经多轮迭代，页面功能基本齐全，但暴露出一类比单点 bug 更麻烦的问题：

- 同一类状态在不同页面口径不一致
- 后端内部 code 直接泄漏到页面
- 当前状态、历史结果、调试信息被混在一起展示
- 空字段、默认值、占位值被当成真实业务信息渲染
- 某些页面只有“说明”，没有“下一步动作”
- 页面布局没有跟信息密度同步收口，重要结论不够突出

这些问题单独看都不一定会报错，但合在一起会让系统出现“技术上能跑，用户却看不懂、判断错、操作错”的情况。

本任务的目标不是继续零散修文案，而是为整个前端建立一套统一的诊断标准，并按同一标准清理所有页面、抽屉和共享展示组件。

## 2. 诊断目标

前端本轮诊断和整改目标：

1. 消除 raw code、默认占位值、无意义空态在 UI 中的直接暴露
2. 明确区分“当前状态”“最近一次结果”“历史记录”“调试上下文”
3. 让每个页面都优先展示真实结论、影响范围和下一步动作
4. 保证所有中文文案为干净 UTF-8，且符合事实
5. 清理旧设计残留、无效组件、无价值区块和死代码
6. 让前端展示和后端真实语义重新对齐

## 3. 适用范围

本任务覆盖以下前端代码：

- `aats/api/static/app.js`

- `aats/api/static/modules/formatters.js`
- `aats/api/static/modules/store.js`
- `aats/api/static/modules/terms.js`

## 4. 诊断分类

### 4.1 文案与术语一致性

检查目标：

- 是否仍有 raw code 直接出现在页面
- 同一概念是否在不同页面使用不同术语
- 是否违反 `frontend_copy_guidelines.md` 中的术语规范、标题模板、按钮命名规则、空状态规范

典型反例：

- `strategy_profile_switch_cooldown_active`
- `post_close_cooldown_active`
- `regime_breakout`
- `operator_restore_ai`

整改要求：

- 所有 code 必须先过 `terms.js` 或共享本地化层
- 页面不得直接渲染原始 reason code
- 同一概念统一使用同一中文说法

### 4.2 当前状态与历史结果混写

检查目标：

- 当前运行模式与最近一次真实决策结果是否被混为一谈
- 当前降级原因与最近一次状态变化是否被混为一谈
- 当前 blocker 与历史 blocker 是否被混为一谈
- 当前操作是否可执行与历史处理记录是否被混在同一块里

典型反例：

- 页面显示“当前运行模式是 AI”，下面又显示“最近一次回退到基础策略”，但没有解释两者不是同一层语义
- 人工恢复后，旧降级原因仍被挂在“当前降级原因”下

整改要求：

- 页面文案必须明确区分：
  - 当前运行状态
  - 最近一次真实结果
  - 最近一次状态变化
  - 历史记录
- 当前视图必须优先显示“现在仍然生效的状态”

### 4.3 空字段、默认值、假字段

检查目标：

- 0、空串、`未请求`、`当前没有额外说明` 是否被当成真实业务信息渲染
- 当某个模块没有真实 payload 时，是否应该整块隐藏，而不是显示空卡片
- 是否存在“页面看起来有数据，其实只是默认填充”的字段

典型反例：

- `被动倾向 0 / 主被动偏向 0`
- `拆单 0 / 参与率 0`
- `未请求 / 未请求`
- `当前成交已落库，但已实现盈亏还在同步`

整改要求：

- 没有真实业务数据时，优先隐藏整块，而不是渲染空内容
- 不允许用默认值伪装成真实数据
- 明确区分：
  - 不存在这个字段
  - 当前无数据
  - 这条链路未启用

### 4.4 动作闭环与控制面完整性

检查目标：

- 页面显示 blocker 时，是否有可执行的处理动作
- disabled 按钮是否说明原因
- 动作执行后页面是否能自动刷新到下一个状态
- 是否存在“有问题但没有处理入口”的死胡同

典型反例：

- 需要复核，但没有复核按钮
- `resume` 灰掉，但页面不告诉用户下一步该做什么
- 页面只展示对账按钮，无法处理 AI review blocker

整改要求：

- 每条主 blocker 至少要有明确动作或明确跳转入口
- 风险页优先展示第一优先级 blocker 的动作面板
- AI 工作台与风险页必须消费同一 blocker/control 数据源

### 4.5 前端展示与后端真实语义对齐

检查目标：

- 前端是否误读后端字段
- 某些指标是否只是进程内计数，重启就丢
- 某些文案是否暗示“稍后会同步”，但后端实际上根本不存这个字段

典型反例：

- “拟下单次数”用进程内计数，服务重启后清零
- “逐笔已实现盈亏还在同步”，但后端根本没有逐笔 realized pnl

整改要求：

- 每个关键展示字段都要能追到真实后端来源
- 前端不能替后端“脑补未来会同步的数据”
- 需要的时候应直接改成符合事实的描述

### 4.6 布局、信息密度与组件形态

检查目标：

- 是否存在大块空白卡片
- 是否存在小卡片承载大数据集
- 是否把高价值结论与低价值说明堆在同一屏
- 页面首屏是否优先展示当前状态和下一步动作

典型反例：

- `AI 状态概览` 占很大面积，但真正高价值信息很少
- `当前持仓` 用小网格，不适合多持仓
- 风险页空历史区块占据大量可视空间

整改要求：

- 高价值结论放首屏
- 多条记录用表格，不用小网格
- 低价值说明、长期历史、辅助诊断应后置

### 4.7 编码与中文质量

检查目标：

- 所有前端源码文件是否能以 UTF-8 正确读取
- 中文文案是否通顺、准确、符合事实
- 是否存在半中半英脏文案
- 是否有 PowerShell 显示误导引发的错误判断

整改要求：

- 文件编码检查必须通过 Python 以 UTF-8 读取验证
- 不根据 shell 显示结果判断是否乱码
- 所有新增和修改文案都必须是干净 UTF-8 中文

### 4.8 历史死代码与旧设计残留

检查目标：

- 已经不再使用的 helper、常量、panel、接口请求是否仍残留
- 页面里是否保留无决策价值的空卡片和旧控件
- store 是否仍在为废弃页面结构请求冗余数据

整改要求：

- 已无消费方的字段、块、按钮、辅助文案、请求规格应删除
- 先删主页面的无价值展示，再评估是否删除后端冗余 payload

## 5. 页面级重点检查项

### 5.1 首页

重点：

- 首要问题与次级提醒是否清楚区分
- 状态说明是否优先表达当前影响和下一步动作
- 不要让首页承担太多调试细节

### 5.2 交易总览

重点：

- 活动委托与当前持仓必须明确区分
- 当前持仓应使用适合多持仓的表格
- 资产概览不要与持仓表重复表达同一信息

### 5.3 策略判断

重点：

- 信号说明、门禁原因、风控结论要做摘要，不要堆原始 reason 列表
- 当前保护规则、本轮执行限制必须本地化并可读

### 5.4 委托与成交

重点：

- 成交记录的“影响摘要”必须符合真实后端字段
- 区分已落库、未同步、字段不存在三种状态
- 现货和合约的说明文案不能混写

### 5.5 风险与恢复

重点：

- 必须优先展示第一优先级 blocker 的动作面板
- 历史记录不能抢占主视图
- 恢复资格、暂停状态、当前根因必须拆开讲

### 5.6 AI 工作台

重点：

- 当前运行模式、最近一轮真实决策结果、最近一次状态变化必须分层
- 没有真实执行建议数据时，不渲染执行建议卡片
- 决策链概览只能展示摘要，不能当 debug dump
- AI review 必须是闭环操作区

### 5.7 AI 配置

重点：

- 只展示当前真正生效的运行参数与策略档位结论
- 自动切换阻断原因必须本地化
- 不再暴露过时 recommendation/activation/rollback 控件

### 5.8 账户与权限

重点：

- 只保留权限管理和账号管理本身
- 不再承载已迁移走的 AI 配置说明

## 6. 技术收口建议

### 6.1 新增共享文案工具层

建议新增前端共享工具模块，统一处理：

- code 列表切分
- 本地化
- 摘要截断
- 空态判断
- “有意义数据”判断

目的：

- 避免每个 view 各自实现一套 `localizeList`
- 避免一页修了，另一页继续泄漏 raw code

### 6.2 前端组件显示规则

统一组件显示约束：

- 没有真实 payload 的模块默认隐藏
- 列表超长默认只展示关键前几项，并给摘要
- 当前状态卡片优先使用 `summaryStrip`
- 大量记录优先用 `responsiveTable`

### 6.3 抽屉与页面必须同口径

要求：

- 页面和抽屉必须使用同一套术语和本地化函数
- 抽屉不能再出现页面已清理掉的 raw code 与 debug 占位文案

## 7. 实施顺序

建议按以下顺序整改：

1. 文档化诊断标准
2. 新增共享前端文案工具层
3. 修 AI 工作台、风险与恢复、交易总览这三个问题最多的页面
4. 再修策略判断、委托与成交、AI 配置、首页、账户与权限
5. 最后统一清理抽屉、死代码和冗余请求

## 8. 验收标准

### 8.1 功能验收

- 页面不再直接显示 raw code
- blocker 有明确动作
- 空字段不再伪装成真实值
- 当前状态、历史状态、最近结果不再混写

### 8.2 文案验收

- 所有新增和修改文案都符合 `frontend_copy_guidelines.md`
- 所有前端源码可用 UTF-8 正确读取
- 中文描述通顺、事实准确

### 8.3 技术验收

- 页面级 Node 渲染冒烟测试通过
- 关键 UI 集成测试通过
- 主要 view 没有未使用 helper / 常量 / 请求规格残留

## 9. 本轮要落实的最小成果

本轮整改至少应完成：

1. 建立共享前端文案工具模块
2. 清理 AI 工作台中的模式/结果/降级原因混写问题
3. 清理执行建议和影子翻译的空数据占位
4. 清理策略判断和 AI 配置中的 raw reason 泄漏
5. 修正委托与成交页中不符合真实后端语义的说明
6. 收口交易总览中的活动委托与持仓表达
7. 清理抽屉中的 raw suggestion / raw blocker 表达
8. 补充对应的前端渲染回归测试
