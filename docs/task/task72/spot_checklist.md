# Task72-B 现货版独立实施清单

## 1. 文档定位

这份清单用于把当前系统升级成“可在强约束下运行现货实盘”的系统。

它是一份独立实施清单，可以单独立项，也可以作为合约优先版完成后的第二条产品线升级路径。

## 2. 成功定义

现货版完成后，系统至少要达到以下状态：

- 能在单账户、单 runtime、单产品线约束下运行现货 `guarded_live`
- 能正确建模可用余额、冻结余额、手续费、成交后资产变化
- 能在重启、乱序、重复回报、REST / WS 抖动下恢复订单状态
- 能对订单、成交、余额、ledger、对账结果做可审计重建
- 能在余额不确定、快照陈旧、对账失败和状态不确定时自动停机

## 3. 适用边界

### In Scope

- OKX 现货实盘
- 现货下单前校验、执行状态机、恢复、对账、自动停机
- 现货可用 / 冻结 / 手续费 / 成交后余额账务闭环
- operator / 控制面 / 报警 / 报表 / UTF-8 中文文案

### Out of Scope

- 杠杆现货、融资融币
- 合约持仓、保证金、资金费、清算模型
- 自动出入金、自动资金调拨
- 高频撮合级策略
- 未通过 `guarded_live` 小资金验证前的高自动化放量

## 4. 实施原则

- 现货余额语义必须独立明确，不能混入合约保证金抽象
- 订单冻结、成交结算、手续费扣减和余额更新必须可审计
- 不允许依赖交易所页面解释余额变化，系统内必须能重建
- 不允许在缺少恢复与对账闭环时打开实盘提交
- 所有新增前端、控制面和报警文案必须是干净的 UTF-8 中文

## 5. 阶段化实施清单

### 阶段 0：共享底座与生产约束

目标：先把当前 runtime 变成可控、可隔离、可审计的真钱运行底座。

主要落点：

- `aats/bootstrap`
- `configs`
- `aats/services/operator`
- `aats/api`
- `aats/storage`
- `tests`

必做清单：

- [ ] 固化 `.env.spot`、runtime profile、YAML 配置和代码默认值的优先级
- [ ] 固化单 runtime、单账户、单环境、单产品线的启动约束
- [ ] 为生产密钥注入、轮换、失效和审计建立明确流程
- [ ] 增加启动前自检，未满足数据库、账户、时钟、关键配置条件时禁止起盘
- [ ] 为 operator 高风险动作增加鉴权、二次确认和完整审计
- [ ] 明确只读、`guarded_live`、恢复态、停机态四类运行口径
- [ ] 把所有新增前端 / operator 文案纳入 UTF-8 中文词典，不允许后端裸字段直出

完成标志：

- 可以给出一份现货生产部署清单
- 任一实例违反单账户或单产品线约束时无法进入交易态

### 阶段 1：现货产品规则与账户语义建模

目标：把“能下现货单”升级成“对现货资产与产品规则有明确模型”。

主要落点：

- `aats/services/market_gateway`
- `aats/schemas`
- `aats/services/execution_engine`
- `aats/services/operator`
- `aats/storage`

必做清单：

- [ ] 拉取并持久化现货产品规则：`tick size`、`lot size`、最小成交额、最大下单量
- [ ] 明确 base / quote 资产语义和下单方向对应的资产占用关系
- [ ] 在订单意图中显式建模现货买卖方向、预估占用资产和手续费影响
- [ ] 对产品规则、资产精度和订单意图做一致性校验，不一致时本地阻断
- [ ] operator 页面提供产品规则快照和账户资产快照

完成标志：

- 任一现货订单在提交前都能回答使用了哪套产品规则和哪组资产约束

### 阶段 2：现货下单前校验与资金冻结语义

目标：在订单提交前确认资金足够、冻结语义正确、失败时不会误放资金。

主要落点：

- `aats/services/execution_engine`
- `aats/services/ledger`
- `aats/services/portfolio_service`
- `aats/storage`
- `tests`

必做清单：

- [ ] 建立买单对 quote 资产、卖单对 base 资产的占用与冻结规则
- [ ] 建立手续费预估、最小成交额、最小可成交数量校验
- [ ] 建立挂单期间的可用余额、冻结余额和剩余可下单额度计算
- [ ] 明确订单拒绝、撤单、部分成交、超时后的冻结释放规则
- [ ] 防止重复回报或恢复重放导致重复释放或重复冻结
- [ ] 给每类阻断场景定义稳定的 reason code 和 UTF-8 中文说明
- [ ] 增加现货余额冻结和释放的单元测试与集成测试

完成标志：

- 任何被拒绝的现货订单都能回答“哪条资金或产品规则阻断了它”
- 挂单和撤单不会把可用余额算错

### 阶段 3：现货执行状态机与恢复硬化

目标：让真实现货订单在提交、确认、部分成交、撤单、超时、重启和重放场景下都能收敛。

主要落点：

- `aats/services/execution_engine`
- `aats/services/recovery_control`
- `aats/services/reconciliation_service`
- `aats/storage`
- `tests`

必做清单：

- [ ] 明确 private WS 与 REST 补拉的状态优先级和冲突处理规则
- [ ] 明确 submit 成功但 ack 丢失、cancel 发出但未确认、order not found 等恢复语义
- [ ] 为 client order id、command id、fill id 建立完整幂等策略
- [ ] 防止重复 fill、重复撤单、乱序回报导致重复结算或错误释放冻结资金
- [ ] 启动恢复时自动识别未知中间态订单，并进入 review 或 halt，而不是继续下单
- [ ] 补齐跨进程重启、事件重放、交易所抖动的集成回归测试

完成标志：

- 任一活跃订单在系统重启后都能恢复到可解释状态
- 不存在重复 fill 导致的重复记账或错误释放冻结余额

### 阶段 4：现货余额、手续费与 ledger 闭环

目标：让现货实盘下的余额变化可以进入完整账务链路。

主要落点：

- `aats/services/ledger`
- `aats/services/portfolio_service`
- `aats/services/reconciliation_service`
- `aats/storage`
- `tests`

必做清单：

- [ ] 建立现货可用余额、冻结余额、成交后余额的投影与存证
- [ ] 明确手续费扣减币种、扣减时点和账务分录
- [ ] 确保 reservation、settlement、ledger、账户快照之间能相互追溯
- [ ] 提供按订单、按资产追踪余额变化的视图或接口
- [ ] 建立现货基线导入、差异分类和补录说明
- [ ] 增加“订单到余额变化”的回归测试矩阵

完成标志：

- 可以从系统数据重建任一时刻的现货资产变化
- 交易所页面不再是解释余额变化的唯一信息源

### 阶段 5：现货对账、自动停机与人工恢复

目标：把“余额或订单状态不确定”明确转成“系统停机并要求人工接管”。

主要落点：

- `aats/services/reconciliation_service`
- `aats/services/recovery_control`
- `aats/services/operator`
- `aats/api`
- `tests`

必做清单：

- [ ] 对账户快照陈旧、余额不一致、fill 不一致、冻结不一致做分类
- [ ] 明确 halt、review_required、resume_blocked 三类状态和处置条件
- [ ] 明确 rebaseline、resume、force resolve 的前置条件、审批要求和审计记录
- [ ] 在关键依赖持续失败、余额差异持续扩大、执行状态无法确认时自动停机
- [ ] 保证恢复流程先拿到新鲜快照，再切换系统状态
- [ ] 所有异常状态都要在 operator 页面给出 UTF-8 中文解释与建议动作

完成标志：

- 对账失败后系统不会继续提交新单
- operator 可以根据控制面信息完成一次完整的审查、恢复或继续停机决策

### 阶段 6：观测、报警与控制面收口

目标：让现货实盘的运行质量、账户健康和异常状态可见、可读、可追踪。

主要落点：

- `aats/services/operator`
- `aats/api`
- `aats/api/static`
- `aats/storage`
- `tests`

必做清单：

- [ ] 增加余额漂移、订单失败率、撤单率、恢复次数、对账漂移等指标
- [ ] 建立现货日报、周报和事故复盘报表
- [ ] 建立关键报警：私有 WS 中断、快照超时、对账失败、重复回报、停机触发
- [ ] 在控制面中按账户、资产、交易对展示当前运行状态和最近异常
- [ ] 建立统一前端词典，所有状态、风险、建议动作统一为干净 UTF-8 中文

完成标志：

- 不需要登录交易所网页，也能从本系统判断当前是否安全运行
- 关键风险信号都具备自动报警和可追溯时间线

### 阶段 7：现货小资金 `guarded_live` 试运行

目标：在严格限制下完成第一轮真钱前向验证。

主要落点：

- `configs`
- `aats/bootstrap`
- `aats/services/operator`
- `aats/services/blocker_control`
- `tests`

必做清单：

- [ ] 限制交易对数量、单笔 notional、单日成交额和最大持仓时间
- [ ] 初始阶段只允许 `guarded_live`，不允许直接进入更高自动化级别
- [ ] 建立每日开盘前检查、盘中巡检、收盘后复盘流程
- [ ] 建立自动停机、人工复核、继续运行、缩容、回退四类判定规则
- [ ] 连续记录真实成交、滑点、手续费、恢复事件和报警事件
- [ ] 小资金阶段未通过前，不允许扩大资金量或增加交易对

完成标志：

- 形成一份连续前向验证报告
- 形成一份是否允许放量的书面结论

## 6. 不允许跳过的硬门槛

以下门槛任何一项未满足，都不允许进入现货真钱提交：

- 无法本地计算并验证可用余额、冻结余额和剩余可下单额度
- 无法在系统内解释手续费和成交后余额变化
- 无法在重复 fill、重启、WS 中断场景下防止重复记账
- 无法在余额不确定或状态不确定时自动停机
- operator 页面无法用清晰 UTF-8 中文表达当前风险和建议动作

## 7. 验收标准

1. 任一现货订单都能回答：
   - 下单前产品规则是什么
   - 下单前资金 gate 结果是什么
   - submit / ack / fill / cancel 时间线是什么
   - 最终如何影响 base / quote 资产和手续费

2. 任一时刻都能回答：
   - 当前可用余额、冻结余额和总余额分别是什么
   - 当前对账状态是否允许继续下单
   - 当前最近一次异常是什么，建议动作是什么

3. 系统必须自动停机以下情况：
   - 账户快照持续陈旧
   - 私有 WS 或关键 REST 持续失败
   - 余额、冻结、fill 对账失败
   - 执行状态无法确认

## 8. 建议首批实际开发任务

建议先拆成以下实际开发工作：

1. 现货生产底座与部署约束
2. 现货产品元数据与账户语义建模
3. 现货下单前资金校验与冻结语义
4. 现货执行状态机与恢复硬化
5. 现货余额、手续费与 ledger 闭环
6. 现货对账、自动停机与人工恢复
7. 现货观测、报警和控制面收口
8. 现货小资金 `guarded_live` 试运行与放量评审

## 9. 结论

现货版是相对更直接的一条真钱升级路径，但它不再是当前默认执行顺序。  
当前如果项目主线先做合约，这份清单依然可以保留为后续第二条产品线的独立实施计划。
